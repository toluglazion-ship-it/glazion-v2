# Image Ingestion Pipeline: R2 upload, identity, and recipe/UMF linkage

**Status:** Implemented (slice 1 of the recipe-to-image retrieval engine)
**Sources:** Glazion Phase Two PRD/TRD v2.0 (§5.3, §5.4, §8, §9, §11), Retrieval Implementation Plan v1.0 (§3, §5.4–5.7, §6, §8, §12, §13)

This document describes how every glaze tile image enters Cloudflare R2, how it is
identified, and how that identity is bound to its recipe and Unity Molecular Formula
(UMF) snapshot so the retrieval engine can trust what it indexes.

Everything downstream (quality scoring, labels, chemistry vectors, Pinecone upserts,
hybrid ranking) consumes the records this pipeline produces. If this layer is wrong,
the retrieval engine ranks the wrong evidence.

---

## 1. Invariants (from the specs, enforced here)

| # | Invariant | Where enforced |
|---|-----------|----------------|
| I1 | PostgreSQL owns business state. R2 owns bytes. Vectors are derived projections. | Whole design |
| I2 | The API generates every object key. Clients never choose a key and never hold R2 credentials. | `ObjectKeyPolicy`, presign endpoints |
| I3 | Bytes bypass the API process. Clients `PUT` directly to R2 with a short-lived presigned URL signed for one key and one content type. | `R2ObjectStorage.CreatePutUrlAsync` |
| I4 | A row exists in PostgreSQL *before* a presigned URL is issued (UPLOAD-05). | Create-then-presign ordering |
| I5 | Completion is proven by `HeadObject`, never by a client flag (UPLOAD-06). | `complete` endpoints |
| I6 | Failed or rejected images are excluded from retrieval, carry a reason code, and are quarantined (IMAGE-03). | `image.validate` job |
| I7 | Bulk import never sets `indexable = true` merely because an object exists; approval is explicit per batch. | `ImportBatch.AutoApprove` default `false` |
| I8 | Every job is idempotent via a dedupe key; retries never duplicate assets or vectors (IMAGE-06). | `ProcessingJobs.DedupeKey` unique |
| I9 | No personal data, capture codes, or signed URLs in object metadata or logs. | Metadata allow-list, logging rules |

## 2. Identity model: how one image links to its UMF and recipe

Each image carries **one canonical identifier** and several **derived identifiers** with
distinct jobs. Confusing them is the most common source of duplicate vectors and broken
links, so they are listed explicitly.

```
                    ┌──────────────────────────────┐
                    │  ImageAsset.Id  (imageId)     │  ← THE canonical identity
                    │  UUID v7, generated by the API│    used by search results,
                    └──────┬───────────────┬────────┘    vectors, labels, feedback
                           │               │
        provenance (1:1)   │               │  chemistry (pinned snapshot)
     ┌─────────────────────┴──┐         ┌──┴──────────────────────────────┐
     │ Upload.Id (mobile)     │         │ RecipeCalculationResult.Id       │
     │   or                   │         │   recipeId + profile + inputHash │
     │ ImportRecord.Id (bulk) │         │   umfJson, fluxTotal, versions   │
     └─────────────────────────┘         └──┬──────────────────────────────┘
                                            │ belongs to
                                         ┌──┴────────────┐
                                         │ Recipe.Id      │ ←── RecipeImages(recipeId, imageId,
                                         └────────────────┘      relationshipType, verified)
```

| Identifier | Type | Scope | Purpose |
|-----------|------|-------|---------|
| `imageId` (`ImageAssets.Id`) | UUID v7 | Global | Canonical ID. Vector IDs are `image:{imageId}:{embeddingVersion}`. Search results, labels, feedback and audit all reference it. |
| `uploadId` (`Uploads.Id`) | UUID | Global | Provenance for mobile captures. Appears in the R2 key. One upload → at most one image asset. |
| `importRecordId` / `externalRecordId` | UUID / string | Global / per batch | Provenance for bulk imports. `externalRecordId` is the dataset's own ID and is unique within a batch. |
| `objectKey` (`ImageAssets.OriginalKey`) | string | Global, unique | Storage address in R2. Derived from `uploadId` or `(batchId, externalRecordId)`. Never from a file name, email, or capture code. |
| `sha256` (`ImageAssets.Sha256`) | hex(64) | Indexed | Content fingerprint computed server-side by streaming the object. Used for integrity and duplicate detection. |
| `recipeId` ↔ `imageId` | join row | `RecipeImages` | Many-to-many with `relationshipType ∈ {test_tile, reference, variant}` and `verified`. |
| `calculationResultId` (`ImageAssets.CalculationResultId`) | UUID | Pinned | The exact UMF snapshot the image was indexed against. Carries `calculationProfile`, `calculationVersion`, `materialAnalysisVersion`, `inputHash`. |
| `sourceVersion` (`ImageAssets.SourceVersion`) | bigint | Per image | Increments on any label/recipe/approval change. Indexing supersedes the old vector only after the new `sourceVersion` is live. |

**Why UUID v7 for `imageId`:** time-ordered UUIDs keep the primary-key B-tree append-mostly
under a 12k+ bulk import and give natural ordering for cursor pagination, while remaining
globally unique and non-guessable enough for the ownership checks that gate every read.

**Why `uploadId` in the key, not `imageId`:** the spec fixes the key layout on `uploadId`
(§9 PRD, §6.2 plan) and the key must exist *before* the image asset does (I4). The asset
is created only once the object is proven present.

**Chemistry status per image** (`ImageAssets.ChemistryStatus`):

| Value | Meaning | Retrieval effect |
|-------|---------|------------------|
| `Missing` | No recipe or UMF supplied | Indexable by text/labels only; chemistry KNN excluded; flagged in result limitations |
| `Pending` | Recipe linked but no calculation snapshot yet | Chemistry KNN excluded until `recipe.calculate_umf` runs |
| `Linked` | `CalculationResultId` pinned | Full chemistry participation |
| `Invalid` | Supplied chemistry failed validation (unknown oxide, non-numeric, flux total not ≈ 1) | Treated as `Missing`; reason recorded on the import record |

## 3. R2 key layout (`ObjectKeyPolicy`)

Bucket: private, e.g. `glazion-assets-prod`. Prefix `prod/` is retained for all environments
so a later promotion does not require object migration. `tenantId` is `default` for now and
retained for the same reason.

```
prod/
  originals/{tenantId}/uploads/{uploadId}/source.{ext}                       ← mobile capture
  originals/{tenantId}/imports/{batchId}/{externalRecordId}/source.{ext}     ← bulk import
  derivatives/{tenantId}/images/{imageId}/display.webp                       ← upright, ≤ 2048 px (§6.1)
  derivatives/{tenantId}/images/{imageId}/thumbnail.webp                     ← upright, ≤ 400 px (§6.1)
  quarantine/{tenantId}/{original key below originals/}                      ← failed validation
```

Rules:

- `ext` is derived from the **declared content type** (`jpg`, `png`, `webp`), not the file name.
- `externalRecordId` is restricted to `[A-Za-z0-9._-]{1,128}` so it is key-safe; anything else is rejected at registration.
- Derivatives are keyed by `imageId`, not `uploadId`, because they belong to the image asset and must survive re-generation without touching originals.
- Quarantine mirrors the original path so reconciliation can map a quarantined object back to its row without a lookup table.

Object metadata is deliberately minimal (plan §6.3). Only these headers are set and signed:

```
Content-Type:            image/jpeg | image/png | image/webp
x-amz-meta-upload-id:    {uploadId}            (mobile)
x-amz-meta-import-record-id: {importRecordId}  (bulk)
x-amz-meta-schema-version: image-asset-v1
```

The SHA-256 is **not** trusted from the client. The worker computes it by streaming the
object and stores it in PostgreSQL, which is the source of truth.

## 4. Two ingestion paths, one convergence point

Both paths converge on `IImageIngestionService.RegisterVerifiedObjectAsync`, which runs in
one PostgreSQL transaction and:

1. creates the `ImageAssets` row (`QualityStatus = Pending`, `ApprovalStatus = Pending`);
2. binds provenance (`UploadId` xor `ImportRecordId`);
3. links the recipe/UMF snapshot if one is supplied;
4. enqueues `image.validate` with dedupe key `image.validate:{imageId}`.

### 4.1 Path A: mobile capture (per image, user-driven)

```
React Native            .NET API                         PostgreSQL         R2
   │  POST /uploads        │                                 │               │
   │──────────────────────►│ validate code/type/size         │               │
   │                       │ insert Uploads(AwaitingUpload)  │──────────────►│
   │◄──────────────────────│ uploadId                        │               │
   │  POST /presign        │                                 │               │
   │──────────────────────►│ key = ObjectKeyPolicy.Upload()  │               │
   │◄──────────────────────│ signed PUT (key, type, meta)    │               │
   │  PUT bytes ───────────────────────────────────────────────────────────► │
   │  POST /complete       │                                 │               │
   │──────────────────────►│ HeadObject ────────────────────────────────────►│
   │                       │ verify size/type                │               │
   │                       │ Uploads → Uploaded              │               │
   │                       │ ImageAssets insert + job enqueue│──────────────►│
   │◄──────────────────────│ status=Uploaded, nextAction=validation          │
```

Retries reuse the same `uploadId`; `complete` is idempotent for already-completed states and
protected by the `ConcurrencyStamp` token against concurrent completion.

Recipe linkage on this path: a capture code with **exactly one** assigned recipe identifies the
recipe unambiguously, so the asset is linked to it (`verified = false`) at completion. A code
with several recipes leaves `ChemistryStatus = Missing` and the curator picks the recipe at
approval (`POST /admin/uploads/{id}/approve` with `recipeId`), which marks the link verified.

### 4.2 Path B: bulk import (12k+ labelled corpus, admin-driven)

Design goals: **no R2 credentials outside the API**, **no bytes through the API**,
**bounded memory on both sides**, **resumable at any point**, **one object per record even
across retries**.

```
Importer CLI (admin token)        .NET API                               R2
   │ POST /admin/imports             │ insert ImportBatches(Open)           │
   │────────────────────────────────►│                                      │
   │◄────────────────────────────────│ batchId                              │
   │                                 │                                      │
   │ for each chunk of ≤200 rows:    │                                      │
   │   sha256 + size (streamed)      │                                      │
   │   POST /imports/{b}/records     │ validate row + chemistry             │
   │────────────────────────────────►│ upsert ImportRecords(Registered)     │
   │                                 │ key = ObjectKeyPolicy.Import()       │
   │◄────────────────────────────────│ [{externalRecordId, objectKey, put}] │
   │   PUT ×N (concurrency 16) ─────────────────────────────────────────────►│
   │   POST /imports/{b}/records/complete {externalRecordIds}               │
   │────────────────────────────────►│ HeadObject ×N (bounded parallel) ───►│
   │                                 │ ImageAssets insert + recipe/UMF link │
   │                                 │ enqueue image.validate ×N            │
   │◄────────────────────────────────│ per-row outcome                      │
   │                                 │                                      │
   │ GET /admin/imports/{b}          │ counts by state (the import report)  │
```

Efficiency properties:

| Concern | Mechanism |
|---------|-----------|
| Throughput | Presigning is local HMAC work (no network), so 200 URLs per call cost ~ms. Uploads run with bounded concurrency (default 16). 12k × ~3 MB finishes in minutes, limited by client bandwidth, not the API. |
| Memory | The CLI streams each file for SHA-256 and streams the `PUT` body. The API never buffers image bytes. The worker streams the object through a hash and keeps only a 1 MiB head for header parsing. |
| Idempotency | Registration upserts on `(batchId, externalRecordId)`. Re-registering an already-uploaded record returns its state without a new URL. Completion is a no-op for already-completed records. |
| Resumability | The CLI persists a state file keyed by `externalRecordId`; a crashed run restarts from the last incomplete chunk. Server-side state is authoritative, so the state file can be deleted safely. |
| Duplicate bytes | The worker indexes `Sha256`; a second asset with the same hash is routed to review with `DuplicateOfImageId` set, never silently dropped or silently indexed. |
| Chemistry fast-fail | UMF rows are validated at registration (before any upload) so a malformed manifest fails in seconds rather than after a 40-minute upload. |

**Manifest row contract** (one JSON object per line, matches plan §13.1 with the storage
address removed, because the API now generates it):

```json
{
  "externalRecordId": "dataset-000123",
  "fileName": "dataset-000123.jpg",
  "contentType": "image/jpeg",
  "tileVariantKey": "white",
  "coneMin": 6, "coneMax": 6, "atmosphere": "oxidation",
  "labels": { "colourFamily": "blue", "surface": "glossy", "opacity": "opaque" },
  "recipeId": null,
  "umf": { "Na2O": 0.18, "K2O": 0.12, "CaO": 0.52, "MgO": 0.18, "Al2O3": 0.35, "B2O3": 0.20, "SiO2": 3.20 },
  "source": "curated_dataset"
}
```

`sizeBytes` and `sha256` are computed by the CLI and sent alongside; the server treats them
as declarations to be verified, never as truth.

## 5. Recipe and UMF linkage at ingestion time

The manifest may supply chemistry in three ways. The outcome is decided per row at
registration and materialised at completion in the same transaction as the asset:

| Manifest input | Action | `ChemistryStatus` |
|----------------|--------|-------------------|
| `recipeId` (existing recipe) | Insert `RecipeImages(recipeId, imageId, test_tile, verified=false)`. If the recipe has a calculation result, pin the newest as `CalculationResultId`. | `Linked` or `Pending` |
| `umf` object (no recipe) | Create a `Recipes` row with `SourceType = Imported`, `SourceReference = {batchId}:{externalRecordId}`; create a `RecipeCalculationResults` row with `CalculationProfile = provided-umf-v1`, `UmfJson` = canonicalised input, `FluxTotal` = Σ flux oxides, `InputHash` = SHA-256 of canonical UMF JSON; link as above. | `Linked` (or `Invalid`) |
| neither | Nothing | `Missing` |

Validation of a supplied `umf` (`ChemistrySchema`, version `oxide-vector-v1`):

- Keys are matched case-insensitively against the 22-oxide fixed order from §11.2 of the PRD. Unknown oxides → `Invalid` with code `unknown_oxide:{name}`.
- Values must be finite, non-negative numbers. Otherwise `Invalid` with `invalid_oxide_value`.
- Flux total (Li2O, Na2O, K2O, MgO, CaO, SrO, BaO, ZnO, PbO) must be within ±0.02 of 1.0 for a UMF. Outside that range the row is accepted but gets warning `flux_total_not_unity`, and the retrieval engine will later renormalise. A flux total of 0 is `Invalid` (`zero_flux`).
- Oxides absent from the input are **not** written as zero. Completeness is preserved so a later confidence calculation can distinguish "unmeasured" from "measured zero" (plan §11.1).

This is deliberately *not* the UMF calculation engine (Phase 3). Supplied UMF values are
stored as provided under an explicit profile name so they can never be mistaken for an
engine-calculated snapshot, and a later re-calculation produces a new `RecipeCalculationResults`
row with a different profile and hash rather than overwriting this one.

## 6. Worker: `image.validate`

Runs on the `ProcessingJobs` queue (PostgreSQL-backed, `FOR UPDATE SKIP LOCKED` claims,
lease timestamps, exponential backoff, dead-letter after `MaxAttempts`). The job is
idempotent: re-running it on a validated image rewrites the same facts.

```
claim job ─► load ImageAsset ─► HeadObject (must exist; else fail missing_object)
   │
   ├─► stream GetObject: SHA-256 over all bytes, keep first 1 MiB
   ├─► sniff format from magic bytes  (not from Content-Type, not from file name)
   ├─► read dimensions (JPEG SOF, PNG IHDR, WebP VP8/VP8L/VP8X)
   ├─► checks → reason codes:
   │     content_type_mismatch     sniffed format ≠ declared type         → Failed
   │     size_mismatch             object size ≠ declared size            → Failed
   │     undecodable_header        no recognisable image header           → Failed
   │     dimensions_exceed_policy  w·h > MaxPixels (decompression guard)  → Failed
   │     checksum_mismatch         declared sha256 ≠ computed             → Failed
   │     below_minimum_dimensions  w or h < policy minimum                → NeedsReview
   │     duplicate_content         same sha256 as an existing asset       → NeedsReview
   │     (none)                                                           → Passed
   │
   ├─► Failed:   CopyObject → quarantine/…, DeleteObject original,
   │             ImageAsset.QualityStatus=Failed, Upload/ImportRecord → Failed + reason
   └─► Passed / NeedsReview:
                 persist format, width, height, sha256, size, etag,
                 QualityPolicyVersion, reasons; Upload → NeedsReview
```

### 6.1 Pixel checks and derivatives (`quality-policy-v2`)

Once the structural checks pass, the same job decodes the bytes it already holds (one read of
the object: hash, header and pixels from the same buffer) with **SkiaSharp** (MIT licence;
ImageSharp's split licence needs a paid licence above a revenue threshold). Only bytes that passed
the header, type and pixel-count checks reach the decoder.

```text
decode at the smallest native scale ≥ 2048 px (JPEG decodes at 1/2, 1/4, 1/8)  → a 48 MP photo never becomes a 48 MP bitmap
apply the EXIF orientation                                                    → derivatives are upright
display.webp    long edge ≤ 2048, quality 82   ┐ PutObject to fixed keys (a retry overwrites);
thumbnail.webp  long edge ≤ 400,  quality 75   ┘ EXIF/GPS metadata is not carried over
original long edge ≤ 400 (LosslessMaxEdge)     → both derivatives lossless WebP, every pixel kept
metrics on a 1024 px grey copy, so scores do not depend on camera resolution:
  sharpness       variance of the 4-neighbour Laplacian   < 40           → blurry       → NeedsReview
  exposure        mean luma < 45, or > 50 % pixels ≤ 8                   → underexposed → NeedsReview
                  > 30 % pixels ≥ 250 (tiles are white: only heavy clipping) → overexposed → NeedsReview
decode error despite a valid header                                      → undecodable_image → Failed, quarantined
original > Derivatives:MaxDecodeBytes (64 MiB)                           → derivatives_skipped_too_large → NeedsReview
```

Pixel reasons only ever send an image to review; they never fail it, because a slightly soft
photo of a rare glaze is still worth a curator's look. All thresholds are configuration
(`Derivatives:*`); the measurements are kept on the asset (`QualityMetricsJson`: sharpness,
meanLuma, darkFraction, clippedFraction, upright width/height, EXIF orientation) so thresholds
can be re-tuned against real data without re-reading the corpus.

`image.derivatives.create` re-creates derivatives and metrics for images validated before this
policy, or after a size change (`POST /api/v2/admin/images/derivatives/backfill`).

Small originals are kept lossless because lossy WebP at quality 82 took the imported corpus's 113 px PNGs (about
14 KB) down to 1–3 KB and visibly blurred them. Derivatives made before this rule are rebuilt with
`POST /api/v2/admin/images/derivatives/backfill` and body `{ "regenerate": true }`; it re-reads each original, so
nothing is lost by having encoded it lossy before. It never
changes an approval; an image still awaiting review whose pixels raise a reason moves from
Passed to NeedsReview. A missing original fails the job at once (`missing_object`).

Search results, admin image detail (`displayUrl`, `thumbnailUrl`) and upload lists
(`thumbnailUrl`, additive to the client contract) use the derivatives when they exist and fall
back to the original otherwise.

## 7. Approval and the hand-off to indexing

`POST /admin/uploads/{id}/approve` now requires `QualityStatus ∈ {Passed, NeedsReview}`
(you cannot approve what the worker has not inspected), optionally attaches a `recipeId`,
sets `ApprovalStatus = Approved`, increments `SourceVersion`, and records who approved.

Bulk batches with `autoApprove = true` perform the same transition inside the worker once
`image.validate` returns `Passed` (never on `NeedsReview`). Default is `false` (I7).

Approval is the boundary of this slice. The next slice enqueues
`index.image.build_document → embed_chemistry → embed_text → upsert` with dedupe key
`image:{imageId}:{embeddingVersion}:{namespace}` and flips `index_records.indexable`.

## 8. API surface added by this slice

```text
POST /api/v2/admin/imports                              create batch; autoApprove is explicit (default false)
GET  /api/v2/admin/imports                              list batches with counts
GET  /api/v2/admin/imports/{batchId}                    import report (counts by state and chemistry outcome)
GET  /api/v2/admin/imports/{batchId}/records            records; filter by status; cursor = externalRecordId
POST /api/v2/admin/imports/{batchId}/records            register ≤200 rows → object keys + presigned PUTs
POST /api/v2/admin/imports/{batchId}/records/complete   HeadObject verify → image assets + chemistry + jobs
POST /api/v2/admin/imports/{batchId}/close
GET  /api/v2/admin/images                               filters (combine): approval, quality, chemistry,
                                                        recipeCode (A03-B2-009 or prefix A03-B2), clayBody (or "none"),
                                                        importBatchId, participantCode, cone ("06" or 6), hasThumbnail,
                                                        q (file name, record id, recipe name or lab code)
GET  /api/v2/admin/images/{imageId}                     one image: provenance, recipe links, pinned UMF snapshot
POST /api/v2/admin/uploads/{uploadId}/approve           now gated on validation; optional { "note": ..., "recipeId": ... }
POST /api/v2/admin/images/derivatives/backfill          { imageIds?, regenerate? } → image.derivatives.create jobs
```

`UploadResponse` gains `imageId` (null until `complete` succeeds) and `nextAction`
(`presign_and_put` → `validation` → `admin_review` → `indexing`) so the mobile state machine
in PRD §6.5 can be driven from the server's view.

The importer CLI lives in `tools/Glazion.Importer` and implements Path B end to end.

## 9. Database additions

| Table | Purpose | Key constraints |
|-------|---------|-----------------|
| `ImageAssets` | One row per image; canonical identity | PK `Id`; unique `OriginalKey`; unique `UploadId`; unique `ImportRecordId`; check exactly one provenance set; index `Sha256`; partial index on `(ApprovalStatus, QualityStatus)` |
| `ImportBatches` | A bulk import run and its policy | PK `Id`; `AutoApprove` default false |
| `ImportRecords` | One row per manifest line | unique `(BatchId, ExternalRecordId)`; unique `ObjectKey`; index `(BatchId, Status)` |
| `RecipeCalculationResults` | Immutable UMF snapshots | unique `(RecipeId, CalculationProfile, InputHash)` |
| `RecipeImages` | Recipe ↔ image links | PK `(RecipeId, ImageId)`; FK restrict on image delete |
| `ProcessingJobs` | Durable job queue | unique `DedupeKey`; partial index `(Status, AvailableAt) where Status='Queued'` |

Existing `Uploads.ObjectKey` now follows `ObjectKeyPolicy` (`prod/originals/default/uploads/{uploadId}/source.{ext}`),
replacing the earlier `users/{userId}/uploads/...` form. There is no production data on
the old layout; the unique constraint on `ObjectKey` is unchanged.

## 10. Failure handling and reconciliation

| Failure | Behaviour |
|---------|-----------|
| Client never `PUT`s after presign | Row stays `AwaitingUpload`/`Registered`; a fresh URL is issued on request; a sweep job (next slice) cancels rows older than the retention window. |
| `PUT` succeeded but `complete` never called | Object exists without an asset. The reconciliation job (`index.reconcile`, next slice) lists `originals/` and reports objects whose key has no `ImageAssets` row. |
| Worker crashes mid-validate | Lease expires; job is re-claimed; SHA-256/dimension writes are idempotent. |
| R2 outage during `complete` | `HeadObject` throws → 503 problem; no row is transitioned; client retries with the same ID. |
| Duplicate manifest rows | Second registration returns the first record's state (upsert on external ID). |
| Same bytes under two external IDs | Both assets exist; the second is `NeedsReview` with `DuplicateOfImageId`; curator decides. The check runs under a transaction-scoped advisory lock keyed on the SHA-256, so two identical files validated concurrently by different workers cannot both pass. |

## 11. What this slice does not do (explicitly)

- Sweep abandoned uploads or list R2 for orphan reconciliation.
- Framing checks (is the whole tile in the picture) or colour calibration against a reference card.
- Decode HEIC/HEIF: the Linux SkiaSharp build has no HEIF codec, so HEIC is still refused at upload.

Done in later slices: pixel checks and derivatives (§6.1), UMF from raw materials
(`docs/features/umf-calculator.md`), vectors and `index_records` (`03-indexing-jobs.md`).

Each of those has a defined hook (job type, status value, or column) in this slice so it can
be added without a schema change to the identity model.
